1. Présentation du projet et objectifs techniques

Le présent rapport documente la conception, la programmation, le déploiement et la validation d'une application Web monopage (Single Page Application) faisant office de portfolio professionnel collectif. Le site sert de vitrine technologique : il présente l'équipe, les compétences individuelles et collectives de ses membres, leurs réalisations — dont les devoirs 1 et 2 du cours — et inclut une passerelle de communication asynchrone avec un serveur d'application.

L'application valide les six compétences avancées énoncées dans la donnée du projet. Le tableau ci-dessous met chacune d'elles en regard de sa réalisation concrète dans le code.

2. Architecture générale de l'application

L'application repose sur une séparation nette entre un client React compilé par Vite et un serveur d'application Express. En production, un seul processus Node.js est exécuté : il sert à la fois le build statique du client et les routes de l'API. Cette unification est ce qui permet un déploiement Railway en une seule commande de démarrage.

2.1 Choix d'architecture et justification

  • Un seul processus en production. Express sert dist/ par un middleware statique, ce qui supprime tout problème de politique d'origine croisée (CORS) entre le client et l'API : les deux partagent la même origine.
  • Appel direct à l'API GitHub depuis le client. Les points de terminaison publics de GitHub n'exigent aucun jeton d'authentification ; faire transiter l'appel par le serveur aurait ajouté une latence et un point de défaillance sans bénéfice de sécurité.
  • Repli SPA côté serveur. La route app.get('*') renvoie index.html pour toute adresse non-API. Sans elle, un rafraîchissement direct sur /equipe produirait une erreur 404, car ce chemin n'existe pas sur le système de fichiers du serveur.
  • Validation dédoublée. Le client valide pour le confort de l'utilisateur ; le serveur revalide car aucune donnée provenant du client n'est digne de confiance — les requêtes peuvent être forgées hors navigateur.

3. Architecture du code client (React)

Le client suit une organisation par responsabilité. Les répertoires components/ et pages/ sont distingués volontairement : un composant de pages/ correspond à une route et compose des éléments de components/, qui eux ne connaissent jamais le routage. Les contenus éditoriaux sont extraits dans data/ afin qu'une mise à jour de texte n'entraîne aucune modification de logique.

3.2 Crochets React employés

  • useState — état local : ouverture du menu, filtre actif, valeurs et erreurs du formulaire, préférences dans le fournisseur de contexte.
  • useEffect — effets de bord : appel réseau à l'API GitHub, mise à jour du titre du document, application de l'attribut data-theme sur <html>, repositionnement du focus au changement de route.
  • useMemo — mémoïsation de la valeur du contexte et de la liste filtrée des projets, afin d'éviter des rendus inutiles.
  • useRef — référence vers l'élément <main> pour y placer le focus.
  • useContext — encapsulé dans le crochet useApplication(), qui lève une erreur explicite s'il est appelé hors du fournisseur.
  • useParams, useLocation — crochets de React Router v6 pour lire l'identifiant du projet et le chemin courant.

6. Gestion de l'état global — Context API

Deux préférences doivent être lisibles depuis pratiquement tous les composants : le thème visuel et la langue d'affichage. Les faire descendre de composant en composant par propriétés aurait imposé de traverser cinq niveaux de hiérarchie pour atteindre une simple étiquette. Context API résout exactement ce problème. 

// src/context/ContexteApplication.jsx (extrait)
const valeur = useMemo(() => {
  const t = (cle) => {
    const dictionnaire = traductions[langue] || traductions.fr;
    return Object.prototype.hasOwnProperty.call(dictionnaire, cle)
      ? dictionnaire[cle]
      : cle;                       // repli : la clé elle-même
  };

  return {
    theme, langue, t,
    estSombre: theme === 'sombre',
    basculerTheme:  () => setTheme(p => (p === 'clair' ? 'sombre' : 'clair')),
    basculerLangue: () => setLangue(p => (p === 'fr' ? 'en' : 'fr'))
  };
}, [theme, langue]);

6.1 Points d'implémentation notables

  • Mémoïsation. Sans useMemo, l'objet de contexte serait recréé à chaque rendu et provoquerait le rendu de tous les consommateurs, même si ni le thème ni la langue n'ont changé.
  • Bascule par attribut, non par classe. L'effet applique data-theme="sombre" sur <html> ; le fichier variables.css redéfinit alors les seules variables de couleur. Aucune règle de mise en page n'est dupliquée entre les deux thèmes.
  • Préférence système respectée. À la première visite, le thème initial est déduit de prefers-color-scheme ; le choix explicite de l'utilisateur est ensuite conservé.
  • Garde-fou. Le crochet useApplication() lève une erreur explicite si un composant l'utilise hors du fournisseur, ce qui transforme une valeur null silencieuse en message de diagnostic immédiat.
  • Langue et accessibilité. Le changement de langue met également à jour l'attribut lang de <html>, indispensable pour que les synthèses vocales emploient la bonne prononciation.

Le gabarit MainLayout est déclaré comme route parente : entête et pied de page ne sont donc jamais démontés lors d'un changement de vue. Seul le contenu de l'Outlet est remplacé, ce qui produit une transition instantanée, sans rechargement ni scintillement.

7.1 Accessibilité de la navigation

Dans une application monopage, un changement de route ne déplace pas le focus : un utilisateur au clavier ou au lecteur d'écran resterait donc positionné sur le lien qu'il vient d'activer, sans percevoir que la page a changé. Le gabarit corrige ce défaut en replaçant le focus sur l'élément <main> à chaque modification du chemin, et un lien d'évitement permet d'atteindre directement le contenu principal dès la première tabulation.

8. Flux de données réseau — API REST de GitHub

La page Équipe injecte des données réelles : pour chaque membre, le nombre de dépôts publics, le nombre d'abonnés et la date d'inscription sont récupérés à l'exécution auprès de https://api.github.com/users/<pseudo>. La logique est isolée dans un crochet personnalisé afin d'être réutilisable et testable indépendamment de l'affichage. 

// src/hooks/useStatistiquesGitHub.js (extrait)
useEffect(() => {
  const controleur = new AbortController();

  async function recupererProfil() {
    setEnChargement(true);
    setErreur(null);
    try {
      const reponse = await fetch(`https://api.github.com/users/${pseudo}`, {
        signal: controleur.signal,
        headers: { Accept: 'application/vnd.github+json' }
      });
      if (!reponse.ok) throw new Error(`Reponse HTTP ${reponse.status}`);
      const charge = await reponse.json();
      setDonnees({ /* … normalisation des seuls champs affichés … */ });
    } catch (exception) {
      if (exception.name !== 'AbortError') setErreur(exception.message);
    } finally {
      if (!controleur.signal.aborted) setEnChargement(false);
    }
  }

  recupererProfil();
  return () => controleur.abort();   // nettoyage au démontage
}, [pseudo, compteurRelance]);

8.1 Les trois états d'un appel réseau

ÉtatRendu correspondantJustification
En chargementIndicateurChargement — rotor animé, role="status"Le critère 2 de la grille exige explicitement des indicateurs de chargement réseau.
ErreurEncadré d'avertissement et bouton « Réessayer »L'API publique de GitHub limite les appels anonymes ; l'échec doit rester lisible et récupérable.
SuccèsListe de description <dl> des trois statistiquesStructure sémantique appropriée pour des couples intitulé / valeur.

Pourquoi un AbortController ?

Si l'utilisateur quitte la page Équipe avant la fin des requêtes, le composant est démonté alors que les promesses sont encore en vol. Sans annulation, leur résolution appellerait setDonnees sur un composant démonté : fuite mémoire et avertissement en console. La fonction de nettoyage retournée par useEffect abandonne la requête, et le bloc catch ignore délibérément l'exception AbortError, qui n'est pas une erreur applicative.

Limite d'appels de l'API GitHub

Les requêtes anonymes sont plafonnées à soixante par heure et par adresse IP. Avec trois membres, chaque affichage de la page Équipe consomme trois appels : la marge est confortable pour une démonstration, mais il faut éviter de recharger la page en boucle juste avant la soutenance. En cas de dépassement, l'interface affiche l'encadré d'erreur — comportement volontaire et documenté, et non un plantage.

9. Architecture serveur — Node.js / Express

Le serveur d'application est configuré dans server.js, à la racine du projet conformément aux spécifications. Il écoute sur le port dynamique attribué par l'hôte Cloud et remplit trois fonctions : servir le build de production, exposer l'API de contact et assurer le repli de l'application monopage.

9.1 Chaîne des intergiciels

app.use(express.json({ limit: '64kb' }));        // 1. analyse du corps JSON
app.use('/api', journalisation);                 // 2. journal des appels API
app.use(express.static(DOSSIER_BUILD, {          // 3. build de production Vite
  maxAge: '1h', index: false
}));
app.get ('/api/sante',    …);                    // 4. sonde de disponibilité
app.post('/api/contact',  …);                    // 5. réception du formulaire
app.get ('/api/messages', …);                    // 6. historique persisté
app.use ('/api',          …);                    // 7. 404 JSON pour l'API
app.get ('*',             …);                    // 8. repli SPA : index.html

app.listen(process.env.PORT || 3000, …);

L'ordre est signifiant. La limite de 64 ko sur le corps JSON écarte les charges utiles abusives dès l'entrée. L'option index: false du middleware statique est indispensable : sans elle, Express servirait dist/index.html pour la racine avant que les routes d'API ne soient atteintes dans certaines configurations. Enfin, le repli app.get('*') est déclaré en dernier, après le gestionnaire 404 de l'API, afin qu'une adresse d'API erronée retourne un message JSON explicite plutôt que la page HTML.

9.3 Persistance des messages

Chaque message validé est normalisé — espaces superflus supprimés, adresse de courriel mise en minuscules — puis complété d'un identifiant unique et d'un horodatage ISO 8601, avant d'être ajouté au tableau contenu dans messages.json. La lecture est tolérante aux pannes : un fichier absent ou corrompu retourne un tableau vide au lieu de faire échouer la requête. 

{
  "id": "msg_1753392000000_k3f9dz",
  "nom": "Marie Dupont",
  "courriel": "marie.dupont@exemple.ht",
  "sujet": "Félicitations",
  "message": "Votre portfolio est très réussi.",
  "recuLe": "2026-07-29T14:20:00.000Z"

Limite assumée : système de fichiers éphémère

Le système de fichiers d'un conteneur Railway est réinitialisé à chaque redéploiement : messages.json ne survit donc pas à une nouvelle intégration sur main. C'est le comportement attendu par l'énoncé, qui demande une persistance dans un fichier local. Une conservation durable exigerait un volume monté ou une base de données — voir la section 15.

10. Intégration, charte visuelle et accessibilité

10.1 Mise en page en CSS pur

Aucun framework ni bibliothèque tierce de style n'est employé : la mise en page repose exclusivement sur Flexbox et CSS Grid. Flexbox structure les éléments linéaires — barre de navigation, pieds de carte, groupes de boutons — tandis que Grid gouverne les dispositions bidimensionnelles. Les grilles s'adaptent sans point de rupture explicite grâce au motif repeat(auto-fit, minmax(…, 1fr)) : le nombre de colonnes découle de la largeur disponible.

10.4 Dispositifs d'accessibilité mis en œuvre

  • Structure sémantique. header, nav, main, section, article et footer délimitent les repères de page ; les rôles banner et contentinfo les explicitent.
  • Hiérarchie des titres. Un unique h1 par vue et aucun saut de niveau — vérification automatisée, section 13.
  • Formulaires. Chaque champ possède un label associé par for/id ; les erreurs sont reliées par aria-describedby, signalées par aria-invalid et annoncées par role="alert".
  • États des commandes. aria-pressed sur les boutons de filtrage et sur la bascule de thème, aria-expanded et aria-controls sur le bouton de menu, aria-current="page" sur le lien de navigation actif.
  • Zones dynamiques. Les indicateurs de chargement et les réponses du serveur sont placés dans des régions aria-live="polite", afin d'être annoncés sans interrompre la lecture en cours.
  • Navigation au clavier. Lien d'évitement en tête de page, contour de focus visible de 3 px sur tout élément interactif, focus replacé sur le contenu principal à chaque changement de route.
  • Images. Toutes les images portent un attribut alt descriptif ; les éléments purement décoratifs — bandeaux colorés, barres du bouton de menu — sont masqués par aria-hidden="true".
  • Mouvement. La requête média prefers-reduced-motion neutralise animations et défilement doux pour les personnes sensibles au mouvement.

12. Déploiement continu sur Railway

12.1 Scripts d'exécution

"scripts": {
  "start": "node server.js",
  "build": "vite build"
}

12.2 Chaîne de déploiement

  1. Le code est poussé sur la branche main du dépôt GitHub public.
  2. Railway, connecté au dépôt, détecte l'intégration et déclenche un build.
  3. npm install puis npm run build : Vite produit le dossier dist/ optimisé et haché.
  4. npm start lance server.js, qui lit le port dans process.env.PORT.
  5. La sonde GET /api/sante confirme la disponibilité et le nouveau déploiement remplace le précédent.

12.3 Configuration déclarative

// railway.json
{
  "build":  { "builder": "NIXPACKS", "buildCommand": "npm run build" },
  "deploy": {
    "startCommand": "npm start",
    "healthcheckPath": "/api/sante",
    "restartPolicyType": "ON_FAILURE",
    "restartPolicyMaxRetries": 5
  }
}

Erreur à ne pas commettre

Ne définissez jamais manuellement une variable d'environnement PORT sur Railway. La plateforme injecte elle-même le port d'écoute ; une valeur figée empêcherait le routeur d'atteindre le conteneur et le déploiement échouerait au contrôle de santé, alors même que l'application fonctionne parfaitement en local.

14.1 Conventions de versionnage

  • Une branche par ensemble de tâches : integration-css, client-react, serveur-devops.
  • Fusion vers main exclusivement par pull request, relue par un coéquipier — la revue de code fait partie des tâches de l'ensemble 3.
  • Messages de commit descriptifs au format type(portée) : description, par exemple feat(contact) : valider le courriel avant l'envoi réseau.
  • Au minimum un commit par membre et par jour de travail, afin que l'historique reflète une contribution réellement équitable.
  • Planification des tâches sur GitHub Projects, en quatre colonnes : À faire, En cours, En revue, Terminé.

15. Limites connues et pistes d'amélioration

LimiteConséquenceAmélioration envisagée
Persistance sur un système de fichiers éphémère messages.json est perdu à chaque redéploiement Monter un volume Railway sur le dossier de l'application, ou migrer vers PostgreSQL
Appels anonymes à l'API GitHub Plafond de 60 requêtes par heure et par adresse IP Faire relayer l'appel par le serveur avec un jeton, et mettre les réponses en cache
Absence de protection contre les envois répétés Un automate pourrait remplir le fichier de messages Limitation de débit par adresse IP, ou question de vérification simple
Aucune notification à la réception d'un message L'équipe doit consulter l'historique manuellement Envoi d'un courriel de notification via un service de messagerie transactionnelle
Contenus éditoriaux figés dans le code Toute mise à jour de texte exige un redéploiement Externaliser src/data/ vers un service de gestion de contenu ou une API dédiée
Tests limités au serveur et au rendu Les interactions utilisateur ne sont pas couvertes Ajouter des tests d'interaction et un scénario de bout en bout automatisé

Conclusion

L'application satisfait l'ensemble des spécifications techniques obligatoires de l'énoncé : découpage en composants React modulaires, navigation sans rechargement par React Router v6, état global centralisé par Context API, consommation asynchrone de l'API REST de GitHub, serveur Express servant le build de production et interceptant le formulaire de contact, persistance des messages en JSON, et déploiement automatisé sur Railway à chaque intégration. Les exigences transversales — mise en page en CSS pur, accessibilité vérifiée et interdiction de innerHTML — ont fait l'objet de contrôles automatisés dont les résultats figurent à la section 13.
